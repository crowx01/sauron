# Reliability, scope, and what lives where

A prompt was recently handed to sauron that read as if sauron owned the
planning loop, iteration counter, retry ceiling, fullscreen TUI, input
field, background-run state, and `run_YYYYMMDD-*.json` artifact store.
**It does not.** Clearing up that boundary once, in writing, so the same
confusion stops recurring.

## The three layers

```
┌────────────────────────────┐
│  user                      │
├────────────────────────────┤
│  orchestrator              │   ← Claude Code, Cursor, Cline, Codex CLI,
│  (CLI/TUI, prompt loop,    │     Aider, or any model behind the generic
│   tool executor, retry,    │     SYSTEM_PROMPT.md.
│   session state, Ctrl-C,   │     This is the thing with a loop, a UI,
│   run artifacts, Bash)     │     and a Bash tool.
├────────────────────────────┤
│  PAL MCP server            │   ← github.com/crowx01/pal-mcp-server
│  (chat / analyze / clink / │     External repo. Hosts the actual model
│   challenge, agentic       │     routing, the agentic toolbelt, response
│   toolbelt, response       │     cache, refusal-memory, classifier,
│   cache, refusal memory,   │     health probe. Registered into the
│   health probe)            │     orchestrator at install time.
├────────────────────────────┤
│  sauron (this repo)        │   ← github.com/crowx01/sauron
│  (installer, skills,       │     Writes CLAUDE.md doctrine, hooks, skill
│   doctrine, selftest)      │     files; registers PAL. Owns NO runtime.
└────────────────────────────┘
```

Sauron's whole product surface, in one line: **it writes the doctrine the
orchestrator reads, and registers PAL once.** After `./setup.sh` finishes,
sauron is not in the hot path. Everything you see at runtime is the
orchestrator obeying the doctrine, using the PAL MCP for model calls, and
executing Bash itself.

## What does NOT live in sauron

| Concern                                                | Lives in                                      |
|--------------------------------------------------------|-----------------------------------------------|
| The planning loop / iteration counter                  | orchestrator (Claude Code)                    |
| Retry ceiling, retry budget                            | orchestrator + `recovery` doctrine the model follows |
| The `Bash` tool that actually runs shell commands      | orchestrator                                  |
| cwd/env state between tool calls                       | orchestrator's `Bash` tool implementation     |
| Fullscreen TUI, input field, Ctrl-C handling           | orchestrator CLI                              |
| Background runs, PID tracking, resume                  | PAL MCP server (agentic toolbelt) + orchestrator |
| `run_YYYYMMDD-*.json` artifact store                   | PAL MCP server                                |
| Model API calls, rate limits, 402/429                  | PAL MCP server                                |
| Response cache, refusal memory, classifier             | PAL MCP server                                |
| MCP server registry on disk (`~/.claude.json`)         | orchestrator (sauron only writes the entry)   |
| API keys at runtime                                    | orchestrator process environment (sourced from `.env.sauron`) |

If a problem lives in one of the right-column rows, the fix is **not in
this repo**. Open an issue (or a PR) against the correct one:

- Orchestrator-side problems (TUI, Ctrl-C, `Bash` tool cwd, retry loop):
  `anthropics/claude-code` (or the vendor of whichever orchestrator you
  chose at install time).
- PAL-side problems (background runs, run artifact files, agentic
  toolbelt, model routing *execution*, 402/rate-limit, response cache):
  `crowx01/pal-mcp-server`.

Sauron's handle on those problems is one lever: the **doctrine** it writes
into `CLAUDE.md` and the SKILL.md files it ships. That doctrine tells the
orchestrator and the PAL-routed models how to behave; it is not a
replacement for fixing a bug in either runtime.

## How a Kali run should flow (post-audit doctrine)

```
   user prompt
        │
        ▼
   orchestrator (Claude Code)
        │
   ┌────┴──────────────────────────────────┐
   │ SessionStart hook injects doctrine     │
   │ UserPromptSubmit hook re-asserts it    │
   │ (sauron's output, cached ~1h)          │
   └────┬──────────────────────────────────┘
        │
        ▼
   plan next action
        │
        │  decides to run a shell command
        ▼
   kali-exec doctrine:
     - absolute path (resolve ~ / $HOME here)
     - subshell if cwd needed
     - capability-first probe BEFORE install
     - PEP 668 ladder, not --break-system-packages
        │
        ▼
   Bash tool call (fresh shell every time)
        │
        ▼
   structured result:
     { command, cwd, exit, stdout_tail, stderr_tail,
       error_class, env_fingerprint }
        │
   ┌────┴──────────────┐
   │ exit = 0          │ exit != 0  OR  error_class set
   │                   │
   ▼                   ▼
 continue plan      recovery doctrine:
                      1. classify
                      2. diagnose (model A)
                      3. independent recheck (model B)
                      4. escalate to pro if disagreement
                      5. apply ONE action
                      6. deterministic verify
                      7. loop detectors + budgets
                      8. INCOMPLETE is never silent
```

## The one hard rule

> `--break-system-packages` is never a shortcut. Capability-first before
> install. Classify every failure before you retry. Change the model
> before you change the plan. Verify before you claim success. Stop
> before the budget stops you.

## Validating this repo

Zero-network, zero-write check that everything shipped here is coherent:

```bash
./setup.sh selftest
# or
npm test
# or
node bin/cli.js selftest
```

The selftest validates:

- Bash / Python / Node syntax of every shipped script.
- YAML frontmatter (`name`, `description`) on every `skills/*/SKILL.md`.
- JSON validity of `settings.example.json` and `package.json`.
- `setup.sh --help` and `cli.js --help` exit cleanly.
- The doctrine-coverage grep: `kali-exec` must document absolute paths,
  PEP 668, capability-first, and the `--break-system-packages` rule;
  `recovery` must document classify, escalation, budgets, verify.
